# Сохранение snapshots изолированных eval-прогонов

## Контекст

`rcode eval run` уже экспортирует `/workspace` после работы модели и безопасно материализует его через `extract_frozen`. Этот каталог используется независимым oracle, но удаляется вместе с временным каталогом host runner. В отчёте остаётся только `snapshot_sha256`, поэтому сравнивать качество исходников разных моделей невозможно.

Нужен явно включённый оператором способ сохранить те же исходники для локального code review, не меняя изоляцию, очистку Docker-ресурсов и сопоставимость отчётов.

## Выбранный подход

Добавить опциональный аргумент `rcode eval run --snapshots <каталог>`. Когда он передан, host runner сразу распаковывает snapshot в постоянный каталог через существующий `extract_frozen`. Без флага сохраняется текущее поведение с временным каталогом.

Рассмотренные альтернативы:

- Копирование временного snapshot после oracle добавляет лишний I/O и отдельную атомарную операцию без улучшения безопасности.
- Сохранение raw tar проще реализовать, но архивы неудобны для сравнения и code review; безопасная распаковка всё равно потребуется позже.

## Интерфейс и жизненный цикл каталога

- Аргумент называется `--snapshots` и принимает путь к новому корневому каталогу.
- Путь должен отсутствовать до запуска. Существующий файл, каталог, symlink или непустой путь не перезаписываются и не используются повторно.
- Rust runner атомарно создаёт корневой каталог с правами `0700` через `DirBuilderExt::mode`, сравнивает canonical path с ожидаемым и передаёт trusted host runner только UTF-8 путь без запятой через существующий invocation по stdin. Эти ограничения исключают небезопасную сериализацию и поздний отказ Docker bind; параллельный процесс с правами того же пользователя не образует отдельную security boundary.
- Для каждого валидированного уникального `case.id` host создаёт `<snapshots>/<case-id>/` с правами `0700` и передаёт его в `extract_frozen`.
- После успешной распаковки существующие права read-only из `extract_frozen` сохраняются. Повторное использование того же пути невозможно благодаря требованию нового корня.
- Без `--snapshots` используется прежний `<temporary>/<case-id>/`; новый аргумент не обязателен и не меняет старые команды.

## Поток данных

1. Agent завершает работу в изолированном контейнере.
2. Trusted host экспортирует только `workspace` из storage keeper.
3. `extract_frozen` проверяет и материализует архив в выбранный постоянный или временный каталог и возвращает SHA-256.
4. Тот же каталог монтируется в observer как `/snapshot` read-only.
5. В отчёт записывается прежний `snapshot_sha256`; абсолютный host-путь в отчёт и comparison key не добавляется.

В snapshot не входят `/agent-home`, provider config, `credentials.json`, OAuth access token, agent JSONL и HTTP receipts. Документация должна явно обозначить snapshots как локальные артефакты: оператор выбирает исключённый из Git каталог и отдельно решает, публиковать ли исходники.

## Обработка ошибок

- Существующий путь `--snapshots`, невозможность создать каталог или получить безопасный абсолютный путь отклоняются до запуска модели и Docker case.
- Ошибка создания case-каталога, экспорта или распаковки обрабатывается по существующему fail-closed пути: кейс не получает PASS, Docker cleanup выполняется, успешный `snapshot_sha256` не выдумывается.
- Незаметного fallback на временный каталог после ошибки постоянного snapshot нет.
- Частично материализованный каталог может остаться после ошибки; он не считается валидным snapshot и не должен использоваться для code review как завершённый результат. Отчёт сохраняет причину класса ошибки без содержимого модели.
- Сохранение исходников не отменяет и не ослабляет удаление контейнеров и volumes.

## Совместимость

- Версия report protocol и comparison key не меняются.
- Наличие постоянного snapshot не влияет на PASS/FAIL: formal и functional verdict вычисляются теми же oracle и policy.
- Поведение без флага байт-за-байт сохраняет прежнюю структуру invocation и отчёта.

## Проверки

- Rust CLI: разбор `--snapshots`, отказ для существующего пути, создание корня `0700`, передача абсолютного пути только при включённой опции.
- Host fixtures: постоянный case-каталог используется для распаковки и oracle; без опции применяется временный каталог; ошибка записи не превращается в PASS.
- Существующие `host_snapshot` tests продолжают проверять traversal, links, duplicate entries, специальные файлы и лимиты.
- Docker fixture: после завершения кейса исходники остаются в заданном корне, oracle использует тот же snapshot, а контейнеры и volumes отсутствуют.
- Стандартные проверки проекта: `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets`, `cargo build --release --locked`, Docker runtime/host и controls.
- Отдельный live-прогон с `--snapshots` выполняется только после fixture-проверок и явно отличается от них.

## Не входит в задачу

- Сохранение agent JSONL, prompt history, provider responses, OAuth-токенов или credentials.
- Автоматическая публикация, архивирование в Git или загрузка snapshots в CI.
- Автоматический code review и новые live-прогоны до завершения реализации и fixture-проверок.
- Изменение model budgets или provider transport.
